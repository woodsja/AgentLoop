# GitHub issue tracking for Pocock planning

This repository-local convention applies when a ChatGPT planner uses Pocock
`to-spec` or `to-tickets` workflows. Keep the globally installed skills and owner
settings unchanged. Reuse existing GitHub issue operations and their shared CLI
transport; do not create another tracker, queue, or scheduler.

Draft publication creates an ordinary GitHub issue with **zero labels**, a
`[DRAFT]` title, and an explicit unauthorized notice. GitHub issues do not have
a native draft state: the notice communicates intent and the absence of labels
keeps these issues out of label-based Ralph admission. The notice alone is not
an admission control. Explicit executable release is a separate owner decision
for the entire batch. This workflow implements no release operation.

## Planner procedure

1. Extract the proposal and testable acceptance criteria from the existing
   planning conversation. Record a durable conversation URL or an owner-readable
   conversation/message reference in `conversation`. Cite the source specification
   as `#N` or its GitHub issue URL in `sourceSpec`. A specification draft may cite
   its parent specification. The planner must check that criteria are verifiable;
   syntax validation cannot determine their quality.
2. Produce JSON using [the blocker-free ticket example](examples/planning-ticket.json).
   `kind` is `spec` or `ticket`; both use the same schema. `id` is a stable,
   repository-scoped lowercase identifier, retained across retries. Required fields
   are `id`, `kind`, `repo`, `title`, `sourceSpec`, `conversation`, `summary`,
   `acceptanceCriteria` (nonempty string array), and `blockers` (integer array).
   Prose fields are nonempty single lines. Optional `labels` must be `[]`.
   Unknown fields, including ready-label settings, are rejected.
3. Generate the complete owner-facing preview locally:

   ```sh
   node src/planning-drafts.js preview docs/examples/planning-ticket.json
   ```

   Review the full output, including every criterion and blocker. The committed
   [full example preview](examples/planning-ticket-preview.md) is generated by
   this command from the owner-supplied #104 planning conversation. No real issue
   was created to generate it.
4. Only when draft publication to the target account is authorized, publish the
   reviewed JSON with the repository helper:

   ```sh
   node src/planning-drafts.js publish path/to/reviewed-draft.json
   ```

   This ticket's implementation/testing authorization excludes real account
   access; use fake GitHub operations for its demonstration. Issue #104 itself
   must remain unlabeled. The examples are not publication instructions for the
   running agent.

**Suppress the normal `to-spec`/`to-tickets` ready-label step completely**, both
on initial publication and on retries. Do not run their usual publication or
post-publication labeling steps. Use their planning output as input to this
repository helper. Do not pass through any labels, including an owner-configured
custom ready label. Do not compensate for failures with `gh issue edit`, add a
label later, enqueue a Ralph job, or modify project registration. The helper
accepts no queue, registration, or release callback. API creation supplies only
title/body, avoiding CLI issue-template label defaults.

## Dependencies and retries

Use [the dependent example](examples/dependent-planning-ticket.json) for blockers.
It renders exactly `Depends on: #104` on its own line. R1 requires one to eight
unique, smaller-numbered same-repository issues. `blockers: []` renders `None.`
and omits the dependency marker entirely. Native GitHub blocking links may be
added separately if available, but never replace R1 metadata. The helper validates
R1 ordering against the allocated issue number; if GitHub returns an unexpected
number, publication is unconfirmed and requires inspection.

The helper lists all issue pages and states to find the stable draft marker
before creating anything. An existing issue must match the complete preview,
be open and unlabeled, and have valid R1 dependencies. Duplicate markers,
changed content, any labels, malformed responses, and closed drafts fail closed.
It never edits, strips labels from, or reopens an existing issue.

A failed or malformed creation response may mean GitHub already created the
issue. Retain the JSON and full error as owner evidence. **Every retry must use
read-only reconciliation**, which never issues another creation request:

```sh
node src/planning-drafts.js retry path/to/reviewed-draft.json
```

If no matching issue is visible, reconciliation fails without writing. The owner
must inspect the ambiguous attempt and confirm that no issue exists before
starting a fresh `publish`; do not blindly rerun `publish` or generate a new ID.
Unexpected labels are an unconfirmed publication requiring owner inspection,
not permission to continue with release. Concurrent initial publishers for the
same ID are unsupported; use one publisher per draft. Server-side automation
that independently labels issues is outside this helper's control and must be
considered by the owner before authorizing publication.

## Delivery and evidence

`node test/planning-drafts.test.js` exercises creation, preview, invalid metadata,
custom and default ready labels, duplicate identity, transport failure, ambiguous
responses, and read-only retries with fake GitHub operations. It verifies the
production `autopilot-projects.json` and `config.json` contents remain unchanged.
`npm test` includes these tests and remains the GitHub CI entry point.

Keep the existing AgentLoop queue, durable execution evidence, independent Claude
review, exact-head-SHA CI, and guarded merge process for delivery. This helper
bypasses none of those controls and changes no production registration or owner
settings. A local test pass is not an independent review, GitHub CI pass, merge,
or verified deployment. Eventual executable release and live rollout each require
their existing separate authorization.
